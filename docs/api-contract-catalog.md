# Product catalog API contract (SCRUM-57)

This document describes the REST contract between the front end (`wwwroot`) and the
ASP.NET Core back end for the product catalog. Originally recorded at commit
`3ed4b95`, it is updated here for SCRUM-54's canonical API integration. Anything that is not in
the code is marked **Planned** and must not be relied on yet.

Related items: SCRUM-39 (database schema), SCRUM-41 (product model), SCRUM-43
(product and category lists), SCRUM-44 (catalog page), SCRUM-45 (product detail),
SCRUM-50 (search), SCRUM-51 (sorting), SCRUM-54 (front end integration).

## 1. Conventions

| Topic | Rule |
| --- | --- |
| Base URL (development) | `http://localhost:5200` |
| Format | JSON, UTF-8, `Content-Type: application/json; charset=utf-8` |
| Property names | camelCase (`stockQuantity`, `categoryId`) |
| Authentication | None. All catalog endpoints are public, read-only `GET` requests. |
| Identifiers | Integers (`id`, `categoryId`) generated by the database. |
| Money | JSON number with two decimals (`43000.00`). The currency is not in the payload; the site shows Turkish lira (TRY). |
| Pagination | **None.** Every list endpoint returns all matching rows in one response. |
| Versioning | None. |
| OpenAPI / Swagger | Not used in this project (no package is installed), so this file is the contract. |
| Ordering | Lists are ordered by `name`, then `id`. Category lists are ordered by category `name`, then `id`. |

## 2. Endpoint overview

| Method and path | Status | Purpose |
| --- | --- | --- |
| `GET /api/health` | Implemented | Liveness check, does not use the database. |
| `GET /api/catalog` | Implemented (SCRUM-44) | Compatible grouped view of categories and active products. |
| `GET /api/products` | Implemented (SCRUM-43/54) | Flat active products, optional category filter; used by products.html. |
| `GET /api/categories` | Implemented (SCRUM-43/54) | Categories used for grouping and homepage links. |
| `GET /api/products/{id}` | Implemented (SCRUM-45) | One active product for the detail page (`product.html`). 404 if unknown or inactive. |
| `GET /api/products?search=` | Implemented (SCRUM-50) | Search by name or description. |
| `GET /api/products?sort=&order=` | Implemented (SCRUM-51) | Sort by price or popularity. |

All implemented endpoints only return **active** products (`IsActive = true`).
Products that are out of stock are **included** on purpose (course requirement 7):
they can be found, but the client must not offer them for the cart.

## 3. Implemented endpoints

### 3.1 `GET /api/health`

No parameters. Response `200`:

```json
{ "status": "ok" }
```

### 3.2 `GET /api/catalog`

Returns every category (also empty ones) with its active products. Retained for
compatible clients; the page now groups the canonical flat list by category ID.

Parameters: none.

Response `200`: array of categories.

| Field | Type | Notes |
| --- | --- | --- |
| `id` | integer | Category id. |
| `name` | string | Category name. |
| `description` | string or `null` | |
| `products` | array | Active products of the category (may be empty). |

Each product in `products`:

| Field | Type | Notes |
| --- | --- | --- |
| `id` | integer | |
| `name` | string | |
| `description` | string or `null` | |
| `price` | number | Two decimals. |
| `stockQuantity` | integer | `0` means out of stock. |
| `imageUrl` | string or `null` | Only `http` and `https` URLs are used by the page. |

Note: this response has no `inStock` flag and no `categoryName`; clients derive
availability from `stockQuantity > 0`.

Example request and response (shortened to one product per category):

```http
GET /api/catalog HTTP/1.1
Accept: application/json
```

```json
[
  {
    "id": 1,
    "name": "Phones",
    "description": null,
    "products": [
      {
        "id": 3,
        "name": "Google Pixel 9",
        "description": "Google smartphone demonstration item",
        "price": 43000.00,
        "stockQuantity": 12,
        "imageUrl": null
      }
    ]
  },
  {
    "id": 2,
    "name": "Tablets",
    "description": null,
    "products": [
      {
        "id": 6,
        "name": "iPad Air",
        "description": "Apple tablet demonstration item",
        "price": 29000.00,
        "stockQuantity": 10,
        "imageUrl": null
      }
    ]
  }
]
```

Errors: `503` (see section 6).

### 3.3 `GET /api/products`

Returns a flat list of active products.

| Query parameter | Type | Required | Behavior |
| --- | --- | --- | --- |
| `categoryId` | integer | No | Only products of this category. An id that does not exist (or is negative) returns `200` with `[]`. A value that is not a valid integer returns `400`. |
| `search` | string | No | Case-insensitive text match on name or description, see section 5.2. |
| `sort` | `price` or `popularity` | No | See section 5.3. |
| `order` | `asc` or `desc` | No | See section 5.3. |

Any other query parameter is **ignored** and the full list is returned.

Response `200`: array of products.

| Field | Type | Notes |
| --- | --- | --- |
| `id` | integer | |
| `name` | string | |
| `price` | number | Two decimals. |
| `stockQuantity` | integer | Never negative (database check constraint). |
| `inStock` | boolean | `true` when `stockQuantity > 0`. |
| `imageUrl` | string or `null` | |
| `categoryId` | integer | |
| `categoryName` | string | |
| `description` | string or `null` | Added by SCRUM-54 to retain catalog descriptions without a second inventory API. |

The response does **not** contain model, serial number, warranty,
distributor, SKU, `isActive` or cost.

Example request and response (all products, shortened):

```http
GET /api/products HTTP/1.1
Accept: application/json
```

```json
[
  {
    "id": 3,
    "name": "Google Pixel 9",
    "price": 43000.00,
    "stockQuantity": 12,
    "inStock": true,
    "imageUrl": null,
    "categoryId": 1,
    "categoryName": "Phones"
  },
  {
    "id": 6,
    "name": "iPad Air",
    "price": 29000.00,
    "stockQuantity": 10,
    "inStock": true,
    "imageUrl": null,
    "categoryId": 2,
    "categoryName": "Tablets"
  }
]
```

Example of an out-of-stock product (TABLET-005 as defined in
`SeedData/seed-products.json`; it is returned like any other product):

```json
{
  "id": 10,
  "name": "Lenovo Tab P12",
  "price": 15000.00,
  "stockQuantity": 0,
  "inStock": false,
  "imageUrl": null,
  "categoryId": 2,
  "categoryName": "Tablets"
}
```

Example with a filter:

```http
GET /api/products?categoryId=2 HTTP/1.1
```

Returns only products whose `categoryId` is `2`.

Errors: `400` (invalid `categoryId`), `503`.

### 3.4 `GET /api/categories`

Parameters: none. Response `200`: array of categories ordered by name.

| Field | Type | Notes |
| --- | --- | --- |
| `id` | integer | Use this value as `categoryId` in `GET /api/products`. |
| `name` | string | Unique in the database. |
| `description` | string or `null` | |
| `parentId` | integer or `null` | Id of the parent category; `null` for a top-level category. Added in SCRUM-123 for the header's category menu. `GET /api/products?categoryId=` of a parent also returns the products of its subcategories. |

```http
GET /api/categories HTTP/1.1
Accept: application/json
```

```json
[
  { "id": 1, "name": "Phones", "description": null, "parentId": null },
  { "id": 3, "name": "Smartphones", "description": null, "parentId": 1 },
  { "id": 2, "name": "Tablets", "description": null, "parentId": null }
]
```

Errors: `503`.

## 4. Data model behind the API

Product (`Products` table, SCRUM-39 and SCRUM-41). The last column shows where a
field is visible today.

| Field | Column type | Required | Public API today |
| --- | --- | --- | --- |
| `id` | INT, auto increment | Yes | `/api/catalog`, `/api/products` |
| `sku` | VARCHAR(64), unique | Yes | No (internal; the seed key is used as SKU) |
| `name` | VARCHAR(200) | Yes | `/api/catalog`, `/api/products` |
| `model` | VARCHAR(100) | Yes | `/api/products/{id}` |
| `serialNumber` | VARCHAR(100) | Yes | No (see open question in section 5) |
| `description` | TEXT | Required when active; nullable for drafts | `/api/catalog`, `/api/products` |
| `stockQuantity` (quantity in stock) | INT, `>= 0`, default 0 | Yes | `/api/catalog`, `/api/products` |
| `price` | DECIMAL(18,2), `>= 0` | Yes | `/api/catalog`, `/api/products` |
| `warrantyStatus` | VARCHAR(100) | Yes | `/api/products/{id}` |
| `distributorInformation` | VARCHAR(500) | Yes | `/api/products/{id}` |
| `imageUrl` | VARCHAR(2048) | No | `/api/catalog`, `/api/products` |
| `isActive` | TINYINT(1), default true | Yes | No (used as a filter: inactive products are hidden) |
| `cost` | DECIMAL(18,2), `>= 0`, nullable | No | **Never public.** Used for profit and loss only. When empty, the effective cost is 50% of the price (`Product.EffectiveCost`, not stored). |
| `categoryId` | INT, foreign key to `Categories.Id` | Yes | `/api/products`, `/api/products/{id}` |

Category (`Categories` table): `id` (INT), `name` (VARCHAR(100), unique, required),
`description` (TEXT, optional).

Category identifiers are the integer `id` values. There are no slugs or codes in the
database (the seed file has codes such as `PHONES`, but they are only used while
loading data).

## 5. Planned contract (not in the code yet)

Everything in this section is a **proposal** for the owners of SCRUM-45, SCRUM-50 and
SCRUM-51 to accept or change. Do not call these from the front end until the items
are merged.

### 5.1 `GET /api/products/{id}` (SCRUM-45, implemented)

This endpoint is now in the code and used by the React product page (`/product`); the behavior below is what it does.

- `{id}` must be an integer. Unknown or inactive product: `404`. Database failure: `503`.
- Response fields: `id`, `name`, `model`, `description`, `price`,
  `stockQuantity`, `inStock`, `imageUrl`, `categoryId`, `categoryName`,
  `warrantyStatus`, `distributorInformation`. Cost and SKU are not returned.
- Decision: the serial number is **not** returned to customers. It identifies
  one physical unit and is only needed by the product manager.

### 5.2 Search: `search` (SCRUM-50, implemented)

| Item | Proposed behavior |
| --- | --- |
| Request | `GET /api/products?search=pixel` |
| Matching | Case-insensitive text match on product `name` or `description`. `%` and `_` are matched as plain characters, not wildcards. |
| Empty value | `search=` (empty or only spaces) is treated as no search. |
| Length | At most 100 characters; a longer value returns `400`. |
| Combination | Can be combined with `categoryId`, `sort` and `order`. |
| Out of stock | Out-of-stock products **must appear** in the results (requirement 7). |
| Response | Same shape as section 3.3, including `stockQuantity` and `inStock`, so the client can block adding an out-of-stock product to the cart. |
| No match | `200` with `[]`. |

The server must also reject adding an out-of-stock product to the cart (SCRUM-49);
hiding a button in the page is not enough.

### 5.3 Sorting: `sort` and `order` (SCRUM-51, implemented)

| Parameter | Allowed values | Default |
| --- | --- | --- |
| `sort` | `price`, `popularity` | Not sent: current order (name, then id). |
| `order` | `asc`, `desc` | `asc` for `price`, `desc` for `popularity`. |

- An unknown `sort` or `order` value returns `400` (`application/problem+json`). `sort` and `order` are not case-sensitive.
- Ties are broken by `name`, then `id`, so the order is stable.
- Proposed meaning of "popularity": the total `Quantity` sold in `OrderItems` whose
  order has `PaymentStatus = Confirmed` and is not cancelled, highest first.
  Fulfillment and payment are separate; do not filter by the removed Paid/Pending
  fulfillment names. Fully refunded orders are excluded; partial-return accounting
  is defined by the later return/refund tasks. Until orders exist every
  product has 0, so the order falls back to name, then id.

### 5.4 Error format for new endpoints

Proposal: use the same `application/problem+json` format as the `503` response
(section 6) for new `400` and `404` answers, so clients can handle every error the
same way.

## 6. Errors and status codes

| Status | When it happens today | Content type | Body |
| --- | --- | --- | --- |
| `200` | Success. Includes an empty list when nothing matches. | `application/json` | JSON as described above |
| `400` | `categoryId` is not a valid integer (for example `?categoryId=abc`, or a number larger than the integer range). | Development: `text/plain`; other environments: none | No stable format. In the Development environment the body is the framework error page with a stack trace; in other environments it is empty. |
| `404` | Unknown path, including `/api/products/{id}` until SCRUM-45 is merged. | none | Empty |
| `405` | A method other than `GET` on a catalog path (for example `POST /api/products`). | none | Empty |
| `500` | Any unexpected error that is not a database failure. There is no custom handler yet. | framework default | Not defined |
| `503` | The database is unreachable or the query fails. | `application/problem+json` | See below |

`503` body (identical for `/api/catalog`, `/api/products` and `/api/categories`):

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.6.4",
  "title": "The catalog is temporarily unavailable.",
  "status": 503,
  "detail": "Please try again shortly."
}
```

The `503` body never contains connection details or SQL. The page shows a retry
button for any failed catalog request.

## 7. Compatibility checks

- Field names and types match the `Product` and `Category` models (SCRUM-41), their
  EF Core configuration and the migrations. `docs/database-schema.md` lists the SCRUM-41 fields and distinguishes
  the current schema from the complete future domain design.
- `stockQuantity` cannot be negative and `price` cannot be negative: both are enforced
  by database check constraints.
- The contract does not require any schema change.

## 8. Proposed decisions for the reviewers

These are recommendations, not agreed decisions. The reviewers can accept or change
them.

1. **Two list endpoints stay, with different jobs.** `GET /api/catalog` remains a
   compatible grouped view. The page now consumes `GET /api/products` and
   `GET /api/categories`; the flat list also supports future filtering, search and
   sorting (SCRUM-50, SCRUM-51). On `/api/catalog`
   clients derive availability from `stockQuantity > 0`; adding an `inStock` field
   later would not break existing clients.
2. **Planned query parameters and the detail endpoint** are accepted as described in
   section 5: out-of-stock products appear in search results, the serial number is not
   shown to customers, and popularity means units sold.
3. **Errors:** new `400` and `404` answers use `application/problem+json`, like the
   existing `503`. The current `400` body for an invalid `categoryId` (stack trace in
   Development, empty otherwise) comes from the framework default and is not a
   designed format; clients must not depend on it. Centralized validation and error
   handling belongs to SCRUM-60.
4. **Data fields:** section 4 matches the models and migrations. The
   [schema documentation](database-schema.md) also includes the SCRUM-41 columns.
